# 인증과 연관관계로 완성하는 FastAPI 웹 서비스

프로젝트 작업 관리 서비스는 로그인한 사용자가 프로젝트를 만들고, 프로젝트에 속한 작업을 등록한 뒤, 작업 상태를 진행 전에서 완료로 변경하는 SSR 웹 애플리케이션이다. 공개 화면과 보호 화면을 분리하고, FastAPI의 `Depends`로 현재 로그인 사용자를 확인한다. 핵심 데이터는 SQLAlchemy ORM과 SQLite에 저장된다.

## 실행 환경

| 항목 | 버전 |
| --- | --- |
| Python | 3.12.3, Dockerfile의 `ubuntu:24.04` 기준 |
| FastAPI | 0.115.6 |
| Uvicorn | 0.34.0 |
| SQLAlchemy | 2.0.36 |
| Jinja2 | 3.1.4 |
| python-multipart | 0.0.20 |
| itsdangerous | 2.2.0 |

직접 의존성은 `requirements.txt`에 고정되어 있다. `starlette`, `pydantic`, `anyio` 같은 하위 의존성은 FastAPI가 설치하는 런타임 의존성이다.

## Docker 실행 방법

```bash
docker build -t ai-assignment-fastapi .
docker run --rm -p 8000:8000 -e SESSION_SECRET=local-secret ai-assignment-fastapi
```

브라우저에서 `http://127.0.0.1:8000`으로 접속한다. 컨테이너 내부에서 SQLite 파일 `app.db`가 생성되고, 애플리케이션 시작 시 테이블과 테스트 계정이 자동으로 준비된다.

## 가상환경 실행 방법

Python 3.10 이상 환경에서 실행할 수 있다.

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python scripts/run.py
```

macOS나 Linux에서는 활성화 명령만 다르다.

```bash
source .venv/bin/activate
python scripts/run.py
```

기본 접속 주소는 `http://127.0.0.1:8000`이다. 다른 SQLite 경로를 쓰려면 `DATABASE_URL`을 지정한다.

```bash
DATABASE_URL=sqlite:///./local.db SESSION_SECRET=local-secret python scripts/run.py
```

## 공개 경로와 보호 경로 정책

| 구분 | 경로 | 접근 정책 | 비로그인 요청 처리 |
| --- | --- | --- | --- |
| 공개 | `/` | 누구나 접근 가능 | 홈 화면에 로그인 버튼 표시 |
| 공개 | `/login` | 누구나 접근 가능 | 로그인 폼 표시 |
| 공개 | `/login` | 누구나 로그인 시도 가능 | 실패 시 실패 문구 표시 |
| 공개 | `/logout` | 세션 초기화 요청 | 세션이 없어도 홈으로 이동 |
| 보호 | `/app` | 로그인 필수 | 401 상태와 로그인 화면 표시 |
| 보호 | `/app/projects` | 로그인 필수 | 401 상태와 로그인 화면 표시 |
| 보호 | `/app/tasks` | 로그인 필수 | 401 상태와 로그인 화면 표시 |
| 보호 | `/app/tasks/{task_id}/complete` | 로그인 필수 | 401 상태와 로그인 화면 표시 |

보호 경로는 `auth/dependencies.py`의 `require_user`가 담당한다. 이 함수는 세션 쿠키에서 `user_id`를 읽고 DB에서 사용자를 조회한다. 사용자가 없으면 `AuthRequiredError`를 발생시키고, `main.py`의 전역 예외 처리기가 로그인 화면을 렌더링한다.

## Depends 기반 인증과 인가 흐름

인증은 요청자가 누구인지 확인하는 단계이고, 인가는 그 사용자가 보호 기능을 사용할 수 있는지 확인하는 단계다. 이 서비스에서는 두 단계를 FastAPI의 `Depends`로 분리했다.

`get_current_user`는 인증 상태를 느슨하게 확인한다. 공개 홈 화면에서도 로그인 여부에 따라 UI를 바꿔야 하므로, 세션에 `user_id`가 없으면 예외를 던지지 않고 `None`을 반환한다. 세션에 `user_id`가 있으면 `get_db` 의존성으로 열린 DB 세션을 사용해 사용자를 조회한다. 조회 결과가 있으면 현재 요청의 사용자 객체가 되고, 없으면 인증되지 않은 요청으로 취급된다.

`require_user`는 보호 경로에서 사용하는 인가 게이트다. `/app`, `/app/projects`, `/app/tasks`, `/app/tasks/{task_id}/complete` 라우터 함수의 매개변수에 `user: User = Depends(require_user)`가 선언되어 있기 때문에 라우터 본문이 실행되기 전에 항상 이 함수가 먼저 실행된다. 사용자가 확인되면 라우터는 `User` 객체를 전달받아 소유자 기준 조회와 상태 변경에 사용한다. 사용자가 없으면 `AuthRequiredError`가 발생하고, 라우터 본문은 실행되지 않는다.

이 구조에서 비로그인 사용자가 차단되는 위치는 보호 라우터가 아니라 `require_user`다. 라우터는 정상 사용자 요청만 처리하고, 실패 응답의 모양은 `main.py`의 예외 처리기가 통일한다. 그래서 보호 경로가 늘어나도 같은 의존성을 붙이는 방식으로 인증 누락을 줄일 수 있다.

## 인증 방식 선택

세션 기반 인증을 선택했다. 이 서비스는 Jinja2 SSR 화면이 중심이고, 브라우저에서 폼을 제출하며, 별도의 API 클라이언트나 토큰 저장소가 필요하지 않다. JWT는 모바일 앱이나 외부 API 소비자가 있을 때 장점이 크지만, 이 과제의 핵심 흐름은 로그인 후 같은 웹 화면에서 프로젝트와 작업을 조작하는 것이다. 따라서 서명된 세션 쿠키에 사용자 ID를 저장하는 방식이 가장 단순하고 요구사항에 맞다.

로그인 성공 시 `request.session["user_id"]`에 DB 사용자 ID를 저장한다. 이후 보호 경로의 `Depends(require_user)`가 같은 세션 값을 읽어 현재 사용자를 확정한다. 로그인 실패 시에는 세션을 만들지 않고 `아이디 또는 비밀번호가 올바르지 않습니다` 문구를 보여 준다. 로그아웃은 `request.session.clear()`로 세션을 제거한다.

사용자 수가 늘어날 때 세션 방식의 장점은 서버가 사용자 ID만 신뢰하고 매 요청에서 DB 사용자 상태를 확인할 수 있다는 점이다. 계정 삭제나 비활성화 같은 변경이 생기면 다음 요청부터 바로 반영된다. SSR 서비스에서는 브라우저가 쿠키를 자동으로 보내므로 프론트엔드가 토큰 저장과 갱신을 직접 처리하지 않아도 된다. 단점은 여러 서버 인스턴스로 확장할 때 세션 서명 비밀값을 모든 인스턴스가 동일하게 가져야 하고, 서버 저장 세션을 선택하는 경우 Redis 같은 중앙 저장소가 필요해진다는 점이다. 이 구현은 서명된 쿠키 세션이라 별도 세션 저장소는 없지만, 쿠키 크기에 담을 수 있는 정보가 작기 때문에 사용자 ID 외의 권한 정보를 많이 넣지 않는 편이 안전하다.

JWT 방식은 REST API, 모바일 앱, 여러 도메인의 클라이언트가 같은 API를 호출하는 구조에서 유리하다. 토큰 자체에 만료 시간과 일부 클레임을 담을 수 있어 서버 저장소 의존을 줄일 수 있다. 대신 로그아웃, 토큰 탈취 대응, 즉시 권한 회수는 별도 블랙리스트나 짧은 만료 시간, 리프레시 토큰 설계가 필요하다. 이 서비스의 현재 요구는 단일 SSR 웹 화면과 로그인/비로그인 구분이므로 세션 방식이 유지보수 비용이 낮다.

## 인증 상태에 따른 UI 변화

로그인 전에는 상단에 로그인 버튼만 표시되고, 홈 화면에는 핵심 기능에 접근할 수 없다는 안내가 표시된다. 로그인 후에는 상단에 `demo님 환영합니다`, 작업 화면 링크, 로그아웃 버튼이 표시된다. 보호 화면인 `/app`에서는 프로젝트 생성 폼, 작업 생성 폼, 프로젝트별 작업 목록이 한 화면에 나온다.

## 도메인 모델과 연관관계

| 모델 | 역할 | 주요 관계 |
| --- | --- | --- |
| `User` | 로그인 사용자이자 프로젝트 소유자 | `User.projects`로 `Project`와 1:N |
| `Project` | 작업을 묶는 업무 단위 | `Project.owner`로 `User`와 N:1, `Project.tasks`로 `Task`와 1:N |
| `Task` | 상태가 바뀌는 작업 | `Task.project`로 `Project`와 N:1 |

양방향 관계는 `relationship`과 `back_populates`로 매핑했다. `User.projects`와 `Project.owner`, `Project.tasks`와 `Task.project`가 서로를 가리킨다. 화면에서는 프로젝트 목록을 조회할 때 소유자와 작업 목록을 함께 로딩하고, `/app`에서 프로젝트 이름, 소유자, 해당 프로젝트의 작업과 상태를 함께 출력한다.

객체 관점에서 `User`는 여러 `Project`를 소유하는 aggregate의 시작점이다. 로그인한 사용자의 대시보드는 사용자가 가진 프로젝트 묶음에서 시작하므로 `User.projects`를 1:N으로 두었다. `Project`는 반드시 한 사용자에게 속하기 때문에 `owner_id` 외래키와 `Project.owner` N:1 관계를 함께 둔다. 이 매핑 덕분에 화면에서는 `project.owner.display_name`처럼 소유자 객체를 따라가서 출력할 수 있고, 서비스에서는 `Project.owner_id == user.id` 조건으로 소유권을 검사할 수 있다.

`Task`는 프로젝트 없이 독립적으로 의미가 약하다. 작업 제목과 상태는 항상 어떤 프로젝트의 맥락 안에서 해석되므로 `Task.project_id`와 `Task.project`를 둔다. 반대로 프로젝트 화면에서는 하위 작업을 함께 보여줘야 하므로 `Project.tasks`를 둔다. 이 양방향 매핑은 DB의 외래키 관계를 객체 탐색으로 표현한 것이다. SQL을 직접 조립하지 않아도 `project.tasks`로 하위 작업 목록을 읽고, `task.project`로 상위 프로젝트를 확인할 수 있다.

양방향 관계를 사용할 때는 순환 참조를 조심해야 한다. `User`를 JSON으로 그대로 직렬화하면서 `projects`를 포함하고, 각 `Project`가 다시 `owner`를 포함하면 끝나지 않는 구조가 될 수 있다. 이 서비스는 Jinja2 템플릿에서 필요한 필드만 출력하므로 객체 전체를 JSON으로 반환하지 않는다. REST API로 확장할 때는 응답 스키마를 별도로 만들고, 소유자 요약이나 작업 요약처럼 한쪽 방향의 필요한 값만 선택해야 한다. 또한 목록 조회에서는 `selectinload(Project.owner)`와 `selectinload(Project.tasks)`로 필요한 관계를 미리 로딩해 템플릿 렌더링 중 반복 쿼리가 과도하게 발생하지 않게 했다.

부모 삭제 정책은 `cascade="all, delete-orphan"`을 사용했다. 사용자가 삭제되면 그 사용자의 프로젝트와 작업은 소유자를 잃고, 프로젝트가 삭제되면 하위 작업은 업무 맥락을 잃는다. 그래서 고아 레코드를 남기지 않는 정책이 이 도메인에 맞다. 해당 이유는 `models/user.py`와 `models/project.py`의 관계 선언 옆 주석에도 남겨 두었다.

## 상태 변경 중심 비즈니스 로직

핵심 상태 변경은 작업 완료 처리다. 작업은 생성될 때 `todo` 상태이며 화면에는 `진행 전`으로 표시된다. 사용자가 `완료 처리` 버튼을 누르면 `services/project_service.py`의 `complete_task`가 현재 사용자의 프로젝트에 속한 작업인지 확인한 뒤 상태를 `done`으로 바꾼다. 화면에는 `진행 전 → 완료` 메시지가 표시되고, 작업 배지는 `완료`로 바뀐다.

상태 변경 로직을 라우터가 아니라 서비스 계층에 둔 이유는 요청 처리와 비즈니스 규칙을 분리하기 위해서다. 라우터는 폼 값을 받고 응답 위치를 결정한다. 서비스는 소유권 확인, 빈 값 검증, 이미 완료된 작업 차단, 상태 변경 전후 라벨 반환을 담당한다. 데이터 접근은 repositories 계층이 맡는다.

단순 CRUD는 데이터를 만들고 읽고 수정하고 삭제하는 방법을 제공하지만, 실제 서비스에서 중요한 규칙은 상태가 바뀌는 순간에 모인다. 작업 완료는 단순히 `status` 값을 수정하는 것이 아니라, 현재 사용자가 해당 작업을 소유한 프로젝트의 사용자인지 확인하고, 이미 완료된 작업을 다시 완료 처리하지 못하게 막고, 변경 전후 상태를 사용자에게 알려야 하는 비즈니스 행위다. 이런 규칙을 서비스 계층에 모아 두면 다른 화면이나 API가 같은 기능을 호출하더라도 동일한 소유권 검사와 상태 전이 규칙을 재사용할 수 있다.


모듈은 바깥쪽 요청 처리와 안쪽 도메인 규칙을 분리하는 기준으로 나누었다. `auth/`는 세션 확인, 비밀번호 검증 보조 함수, 인증 예외처럼 로그인 여부를 판정하는 코드를 담는다. `routers/`는 URL, HTTP 메서드, 폼 파라미터, 리다이렉트 같은 웹 입출력만 담당한다. `services/`는 프로젝트 생성, 작업 생성, 작업 완료처럼 사용자의 의도가 도메인 상태를 어떻게 바꾸는지 결정한다. `repositories/`는 SQLAlchemy 조회와 저장을 캡슐화해 서비스가 쿼리 세부사항에 직접 묶이지 않게 한다. `models/`는 테이블, 외래키, 관계 선언을 담고, `templates/`는 사용자에게 보이는 SSR 화면만 담당한다.

이 기준을 적용하면 변경 이유가 파일 경계와 맞아떨어진다. 로그인 차단 정책을 바꾸면 `auth/`와 일부 라우터 의존성 선언을 보면 되고, 작업 완료 규칙을 바꾸면 `services/project_service.py`를 보면 된다. DB 조회 최적화가 필요하면 `repositories/`에서 쿼리를 조정하고, 화면 문구나 배지를 바꾸면 `templates/`를 수정한다. 한 파일에 인증, 쿼리, 상태 변경, HTML 조립이 섞이지 않기 때문에 요구사항이 커져도 수정 범위를 추적하기 쉽다.

사용자 관점의 흐름은 홈 접속, 로그인, 작업 화면 진입, 프로젝트 생성, 작업 생성, 완료 처리, 결과 확인이다. 개발자 관점의 흐름은 라우터가 요청을 받고, 인증 의존성이 현재 사용자를 결정하며, 서비스가 비즈니스 규칙을 실행하고, repository가 DB를 조회 또는 저장한 뒤, Jinja2 템플릿이 결과를 렌더링하는 구조다.

새로운 역할을 추가한다면 먼저 `User` 모델에 `role` 같은 컬럼을 추가하고, 테스트 계정 생성 로직에 역할 값을 넣어야 한다. 그 다음 `auth/dependencies.py`에 `require_admin` 또는 `require_role("admin")` 같은 보호 의존성을 추가한다. 관리자만 접근할 라우터에는 `Depends(require_admin)`을 붙이고, 템플릿의 내비게이션은 현재 사용자 역할에 따라 관리자 메뉴를 보여 주도록 조정한다. 여러 역할이 데이터 접근 범위를 다르게 가져야 한다면 서비스 계층의 소유권 검사와 repository 조회 조건도 함께 바꿔야 한다. 단순히 버튼만 숨기는 것은 보안이 아니므로 서버 의존성에서 먼저 차단해야 한다.

REST API와 별도 프론트엔드로 전환하면 인증 처리 방식도 달라진다. SSR에서는 서버가 세션 쿠키를 읽고 바로 템플릿을 렌더링하지만, 분리형 프론트엔드는 API 응답으로 JSON을 받고 화면 상태를 직접 관리한다. 세션 방식을 유지한다면 CORS, SameSite, Secure 쿠키, CSRF 방어를 명확히 설정해야 하고, API의 401 응답을 프론트엔드 라우터가 로그인 화면 이동으로 처리해야 한다. JWT로 바꾼다면 로그인 API가 액세스 토큰을 발급하고, 프론트엔드는 `Authorization: Bearer ...` 헤더를 붙여 보호 API를 호출한다. 이 경우 토큰 저장 위치, 만료 처리, 리프레시 토큰 회전, 로그아웃 시 토큰 폐기 정책을 별도로 설계해야 한다.

## 위협 모델과 보안 판단

이 서비스는 학습용 SSR 웹 애플리케이션이며 복잡한 역할 기반 권한 체계는 구현하지 않았다. 보호 대상은 프로젝트와 작업 화면 전체이고, 인가 기준은 로그인 여부와 데이터 소유자 일치 여부다. 작업 생성과 상태 변경 시 DB 조회 조건에 현재 사용자 ID를 포함해 다른 사용자의 프로젝트나 작업을 조작하지 못하게 했다.

세션 쿠키는 `SessionMiddleware`가 서명하므로 클라이언트가 `user_id`를 임의로 바꾸면 서명이 맞지 않는다. 운영 환경에서는 `SESSION_SECRET`을 반드시 예측하기 어려운 값으로 지정해야 한다. HTTPS 환경에서는 `https_only=True`로 바꾸고, 쿠키 보안 속성을 더 엄격하게 설정하는 것이 맞다.

비밀번호는 평문으로 저장하지 않고 PBKDF2-SHA256 해시로 저장한다. 외부 라이브러리 범위를 줄이기 위해 표준 라이브러리를 사용했다. 운영 서비스라면 비밀번호 정책, 계정 잠금, CSRF 방어, 감사 로그, 비밀값 관리, DB 마이그레이션 도구를 추가해야 한다.

## 문제 해결

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 로그인 후에도 `/app`에서 로그인 화면이 보임 | 브라우저 쿠키가 오래된 세션을 들고 있음 | 브라우저 쿠키를 삭제하거나 로그아웃 후 다시 로그인 |
| 서버 시작 시 `ModuleNotFoundError` 발생 | 프로젝트 루트가 아닌 위치에서 실행 | 저장소 루트에서 `python scripts/run.py` 실행 |
| 폼 제출이 422를 반환 | 필수 폼 값 누락 | 프로젝트 이름, 작업 제목, 프로젝트 선택 값을 입력 |
| DB를 새로 시작하고 싶음 | 기존 `app.db`가 남아 있음 | 서버를 중지하고 `app.db` 삭제 후 재실행 |
| Docker 컨테이너 재시작 후 데이터가 사라짐 | 컨테이너 내부 SQLite 파일을 사용함 | 데이터 보존이 필요하면 볼륨을 마운트하고 `DATABASE_URL` 경로를 볼륨 내부로 지정 |

## 검증 증거

검증은 Ubuntu 24.04 기반 Docker 컨테이너에서 수행했다. 의존성 설치, 서버 실행, HTTP 시나리오 확인, 컴파일 확인, Docker 이미지 빌드를 모두 컨테이너 또는 Docker 빌드 환경에서 실행했다.

| 증거 파일 | 확인 내용 |
| --- | --- |
| `evidence/verification.log` | 비로그인 `/app` 접근 차단, 로그인 실패 안내, 정상 로그인, 프로젝트 생성, 작업 생성, 완료 상태 변경 |
| `evidence/verification-container.log` | Ubuntu 24.04 컨테이너에서 의존성 설치 후 `scripts/verify.py`와 컴파일 검사를 실행한 통합 로그 |
| `evidence/runtime.log` | 빌드된 Docker 이미지가 `/`와 `/login` 화면을 실제로 응답 |
| `evidence/compile.log` | `python -m compileall -q .` 통과 |
| `evidence/docker-build.log` | Dockerfile 기반 이미지 빌드 성공 |

`evidence/verification.log`의 핵심 결과는 다음과 같다.

```text
비로그인 /app 접근 상태: 401
잘못된 로그인 상태: 401
정상 로그인 후 상태: 200
프로젝트 생성 상태: 200
작업 생성 상태: 200
작업 완료 상태 변경 상태: 200
```

자동 검증을 다시 실행하려면 다음 명령을 사용한다.

```bash
python scripts/verify.py
```

이 명령은 검증용 SQLite DB를 만들고, Uvicorn 서버를 실행한 뒤, 로그인부터 상태 변경까지의 HTTP 흐름을 수행하고 `evidence/verification.log`를 갱신한다.
