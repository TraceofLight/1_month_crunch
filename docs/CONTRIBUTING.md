# 협업 규칙

## 브랜치 전략

`main`은 팀 기준에서 항상 실행 가능한 상태를 유지한다. 모든 작업은 `feature/*` 브랜치에서 진행하고, PR 리뷰와 승인 후 `main`에 병합한다. 공유 브랜치에서는 강제 푸시와 합의 없는 히스토리 재작성을 금지한다.

GitHub Flow를 선택한 이유는 기능 단위 브랜치와 PR 리뷰 흐름이 단순해서 3~5인 팀이 같은 규칙으로 반복하기 쉽기 때문이다. `main`을 깨지지 않는 기준선으로 두면 충돌과 실수 커밋의 영향을 빠르게 발견할 수 있다. 배포 브랜치를 여러 개 두지 않아도 학습 과제의 협업 목표를 충족한다.

## 브랜치 네이밍 규칙

브랜치 이름은 `feature/<name>-<topic>` 형식을 사용한다.

예시는 다음과 같다.

| 작업자 | 작업 | 브랜치 |
| --- | --- | --- |
| 김민서 | 수학 유틸 추가 | `feature/kim-min-seo-math-utils` |
| 이지현 | 리뷰 규칙 작성 | `feature/lee-ji-hyun-review-guide` |
| 박서연 | 충돌 기록 작성 | `feature/park-seo-yeon-conflict-log` |
| 최준호 | 트러블슈팅 기록 작성 | `feature/choi-jun-ho-troubleshooting` |

## 커밋 메시지 컨벤션

커밋 메시지는 `type: subject` 형식을 사용한다. subject는 무엇을 바꿨는지 알 수 있게 구체적으로 작성한다.

허용 type은 다음과 같다.

| type | 의미 |
| --- | --- |
| `feat` | 기능 또는 예시 코드 추가 |
| `fix` | 결함 수정 |
| `docs` | 문서 추가 또는 수정 |
| `refactor` | 동작을 유지한 구조 개선 |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 실행 환경, 설정, 기타 유지보수 |

금지 예시는 `update`, `fix`, `temp`, `wip`, `final`, `bug fix`, `edit file`이다. 이런 메시지는 변경 대상과 이유를 알 수 없어 리뷰와 추적에 도움이 되지 않는다.

## PR 작성 규칙

모든 PR 본문에는 다음 항목을 포함한다.

| 항목 | 기준 |
| --- | --- |
| 연결 이슈 | `Closes #이슈번호` 또는 `Fixes #이슈번호` |
| 변경 사항 | 무엇을 바꿨는지 파일 또는 기능 단위로 설명 |
| 변경 이유 | 왜 이 변경이 필요한지 설명 |
| 테스트/검증 | 실행한 명령, 수동 확인 절차, 남긴 증빙 |

PR은 최소 1명의 승인을 받은 뒤 병합한다. 작성자는 리뷰 코멘트에 답글을 남기고, 반영한 경우 추가 커밋 또는 수정 내용을 기록한다.

## 코드 리뷰 규칙

리뷰는 `LGTM`이나 `좋아요`만으로 끝내지 않는다. 각 PR에는 파일, 라인, 동작, 문서 근거 중 하나를 들어 실질 코멘트를 1개 이상 남긴다.

좋은 리뷰 코멘트 예시는 다음과 같다.

| 상황 | 코멘트 예시 |
| --- | --- |
| 모호한 이름 | `src/team_utils.py`의 함수명이 검증 대상을 충분히 드러내지 않아 `commit_message_status`처럼 결과 성격을 포함하면 좋겠습니다. |
| 누락된 검증 | README에는 실행 명령이 있지만 증빙 파일 경로가 없어 재현 결과를 확인하기 어렵습니다. |
| 충돌 위험 | 같은 hunk를 여러 문서 PR에서 동시에 수정하므로 한 PR을 먼저 병합한 뒤 나머지 PR은 최신 `main` 기준으로 다시 확인해야 합니다. |

## 충돌 대응 흐름

충돌이 발생하면 작성자는 PR 코멘트나 팀 채널에 충돌 파일과 브랜치를 공유한다. 상대 작업자와 함께 최종 의도를 확인하고, 충돌 마커의 각 영역이 어떤 변경을 뜻하는지 비교한다. 해결 후에는 `docs/conflict-resolution.md`에 상황, 마커, 명령, 선택 이유, 결과를 기록한다.

## 보호 규칙

`main` 브랜치는 직접 push를 금지한다. PR을 통한 병합만 허용하고, 최소 1명 승인을 요구한다. 팀 합의 없이 `main`에 대해 `git reset`, `git rebase`, 강제 푸시를 실행하지 않는다.

## 긴급 핫픽스 규칙

긴급 수정도 `main`에 직접 push하지 않는다. 먼저 이슈에 증상, 영향 범위, 재현 절차를 적고 `main` 기준으로 `feature/<name>-hotfix-<topic>` 브랜치를 만든다. 수정 범위는 원인 파일로 제한하고, Docker 컨테이너에서 재현과 수정 후 검증을 실행한다.

핫픽스 PR 본문에는 `Closes #이슈번호`, 변경 사항, 변경 이유, 테스트/검증 방법을 포함한다. 최소 1명 리뷰어가 원인과 부작용 가능성을 확인한 뒤 approve하면 `main`에 병합한다. 임시 대응이면 후속 이슈를 만들어 정리 작업을 별도로 추적한다.

## 반복 충돌 예방

충돌이 반복되면 충돌 파일, 충돌 hunk, 최근 병합 순서, 같은 문단을 수정한 PR 수를 확인한다. 작업 범위 중복이 원인이면 한 PR을 기준 변경으로 먼저 병합하고 다른 PR은 최신 `main` 기준으로 다시 확인한다. 파일 이동과 내용 수정이 겹친 경우에는 경로 변경 PR과 내용 수정 PR을 분리한다.

README의 공통 문단, 제출 인덱스 표, 요구 파일명은 동시에 여러 PR에서 수정하지 않는다. 문서 구조나 파일 경로를 바꾸려면 먼저 이슈에서 합의하고, 과제 요구 경로와 외부 링크가 깨지지 않는지 확인한다.

## rebase 안전 수칙

`git rebase`는 개인 feature 브랜치 히스토리를 정리할 때만 사용한다. `main`, 이미 병합된 브랜치, 다른 팀원이 기반으로 삼은 공유 브랜치에서는 rebase하지 않는다.

rebase는 커밋 SHA를 바꾸므로 공유 브랜치에서 사용하면 다른 팀원의 히스토리와 어긋날 수 있다. 원격에 올린 개인 브랜치에 rebase가 꼭 필요하면 팀에 먼저 알리고, 일반 강제 푸시 대신 `--force-with-lease`를 사용한다. rebase 후에는 테스트와 `git log --oneline --graph --all`로 중복 커밋과 의도하지 않은 변경을 확인한다.
