# README Evaluation Hardening Design

## Goal
현재 `e1-2` 브랜치의 README를 과제 제출 문서 + 설명 문서의 균형 형태로 보강한다.

핵심 목표:
- 현재 기능 설명 장점은 유지한다.
- AI Codyssey가 Fail 처리한 설명형 평가 항목을 직접적으로 보강한다.
- 스크린샷/증빙은 사용자가 나중에 채울 수 있도록 자리표시자를 함께 남긴다.

## Current State
현재 README는 다음 강점이 있다.
- 프로젝트 개요, 실행 방법, 기능 목록, 파일 구조, `state.json` 스키마 설명이 있다.
- 현재 구현된 보너스 기능까지 반영되어 있다.
- 클래스 구조와 테스트 항목을 간단히 설명하고 있다.

현재 README의 약점은 다음과 같다.
- 퀴즈 주제 선정 이유가 없다.
- 설명형 채점 항목을 직접적으로 답하는 문장이 부족하다.
- Git 커밋, 브랜치, merge, clone, pull 관련 증빙 섹션이 약하다.
- 심층 인터뷰 대비 설명이 거의 없다.
- 평가자가 실제로 무엇을 확인해야 하는지 안내하는 자리표시자가 부족하다.

## Design Direction
현재 README 구조를 완전히 갈아엎지 않고, 기존 흐름을 유지하면서 과제 평가에 필요한 설명형 섹션을 추가한다.

원칙:
- 기능 설명은 유지한다.
- 채점 기준에 대응하는 설명은 별도 섹션으로 보강한다.
- Git/스크린샷 증빙은 설명과 자리표시자를 함께 둔다.
- 이미 구현된 보너스 기능은 유지하되, 본과제 기준 설명이 흐려지지 않도록 균형을 맞춘다.

## Recommended README Structure
README는 아래 흐름으로 정리한다.

1. 프로젝트 개요
2. 퀴즈 주제와 선정 이유

4. 실행 방법
5. 기능 목록
6. 파일 구조
7. 데이터 파일 설명 (`state.json`)
8. 클래스 구조와 책임 분리
9. 입력 처리 / 게임 진행 / 저장-불러오기 흐름 설명
10. 예외 처리 설명
11. Git 작업 전략 설명
12. clone / pull 실습 설명 및 증빙 자리표시자
13. 실행 결과 및 검증 체크리스트
14. JSON 사용 이유와 한계
15. 심층 인터뷰 대비 설명

## Placeholder Style
자리표시자는 문서에 자연스럽게 포함한다.

형식 예시:
- `(여기 git log --oneline --graph 스크린샷 필요)`
- `(여기 clone 실습 화면 스크린샷 필요)`
- `(여기 메뉴 화면 스크린샷 필요)`

원칙:
- 사용자가 나중에 쉽게 채울 수 있게 구체적으로 적는다.
- 어떤 증빙이 필요한지 바로 알 수 있게 한다.

## Scope Control
이번 작업에서 할 일:
- README만 보강한다.
- 설명형 평가 항목을 채우는 데 집중한다.
- 코드 변경은 하지 않는다.
- 스크린샷은 직접 넣지 않고 자리표시자만 둔다.

이번 작업에서 하지 않을 일:
- 코드 구조 리팩터링
- 기능 추가
- 테스트 수정
- Git 히스토리 재작성

## Success Criteria
다음이 충족되면 성공이다.
- README가 과제 제출 문서로서 필수 항목을 갖춘다.
- 기능 설명뿐 아니라 설명형 채점 항목에 대한 답변이 문서에 포함된다.
- Git/clone/pull/스크린샷 관련 증빙 위치가 자리표시자로 명확히 남는다.
- 현재 보너스 기능 설명은 유지하되, 본과제 평가 관점이 더 분명해진다.
